# Research and decisions

User selected Sled authority + LanceDB retrieval after workload analysis. Maintainability/modularity are explicit requirements. Android voice transcription is owner-tested; default-assistant activation remains deferred until backend utility is real. User is merging worktree023 concurrently; isolate025 and review the merged storage API before Lance integration.

Existing home-agent stores have useful behaviour but separate read/modify/write paths and default Sled durability do not yet establish the desired command acknowledgement contract. Session arrays are replaced as a whole. New namespaces/API avoid silently reinterpreting legacy data; migration is explicit later.

Pinned dependencies at base: Sled0.34.7; LanceDB0.40.0/Lance13. New foundation reuses locked serde/chrono/uuid/async-trait/tokio/thiserror versions. Sled's documented atomic batches, serializable transactions and explicit flush support the selected owned-DB/mutex/atomic-batch design. The single-process ownership constraint matches a private backend serving many clients. All Sled operations are offloaded to blocking workers.

Source audit through agentic-nix after the jail restart: `crates.io::sled-0.34.7`, `src/tree.rs::apply_batch_inner` seals a recovery guard for all-or-none recovery. `src/pagecache/logger.rs::flush` and `src/tree.rs::Drop` also confirm that both acknowledgement and final destruction can perform blocking I/O. The adapter therefore offloads destruction as well as read/write/flush and exposes an awaited close for immediate reopen. These source guarantees are distinct from physical power-loss qualification.

Merged code-index review: `agentix-store/src/lib.rs` owns code/GitHub collection keys and a required embedding model/dimension profile. Its Arrow 58 row batches, typed FTS queries and single-row merge patterns are reused in the separate personal adapter without importing the code-index record schema or defaults. The initial personal profile is `personal-lexical-v1` (zero vector dimensions); semantic model quality/evaluation remains unperformed T011 work.

## First conversational acceptance findings (2026-10-29)

The configured gateway at ai.lan.disasm.us:11434 is reachable and lists the already-installed Qwen2.5-7B-Instruct Q8_0 model. Structured decisions go through the existing local router/gateway path; no model download, backend swap or deployment was performed.

Initial native JSON-schema generation failed with `grammar init: NullGrammar`. Exact pinned llama-cpp-sys-2 0.1.154 source, retrieved through agentic-nix, defines `MAX_REPETITION_THRESHOLD 2000` in `llama.cpp/src/llama-grammar.cpp`; `common/json-schema-to-grammar.cpp::build_repetition` emits bounded repetitions for maxLength. Our4096-character schema bound exceeded that limit. Removing that native repetition bound fixed initialization; the JSON action shape remains constrained, while Rust validates UTF-8 byte limits and the adapter enforces token/output/response bounds.

Live synthetic grocery add and read then passed, around0.6–1.2seconds per warm request. The generic update-record correction failed twice: Qwen selected the list's ID and copied its unchanged body instead of changing the pineapple item to mango. Storage assertions caught the failure despite the original update acknowledgement. A deterministic no-op guard now asks for clarification and preserves the original revision. At that checkpoint the live suite remained incomplete; these timings did not qualify overall model quality or memory use.

Owner approved replacing generic replacement with focused edit tools after reviewing the failure. `edit_list_item` now changes text while preserving list_id/completed; `set_task_completed` preserves title/due_at. Both validate original type/revision; unchanged edits produce no mutation. Existing stored domain commands and prepared plans remain compatible. Actual-Sled tests cover wrong targets, stale revisions, unchanged edits, preserved fields and replay. The first live rerun instead failed at grocery creation because Qwen supplied a nonexistent list ID; deterministic resolution rejected it without writes. The new-list prompt now explicitly requires null when no matching list exists. Android integration remains gated on broader conversational acceptance; no default-assistant switch or phone changes were made.

With focused tools, grocery correction passed repeatedly. A subsequent live task request was misclassified as a list item; explicitly prioritizing the latest task/note instruction fixed that case. Adding task completion exposed expected_revision=2 for an original task at revision1: all three initial repeat trials rejected it without effects. The prompt now explicitly requires the target's current revision, not its next revision. Three fresh-store trials then passed all eight operation/replay cases; three more trials after everyday-language clarification guidance also passed (final logs `/tmp/agentix-025-focused-acceptance-{1,2,3}.log`, about0.5–1.2seconds per warm request).

Acceptance limits: these checks establish actual mutation/read/replay behavior for a small synthetic corpus, not general model reliability or clarification quality. In the final trials the unsupported email case wrote nothing but asked whether to email the list; this incorrectly implies a capability. Ambiguous-time questions also need broader quality evaluation. Keep Android/live deployment gated on that remaining conversational acceptance, and do not infer readiness from green storage/status assertions. No runtime VRAM measurement or physical phone acceptance was performed.
