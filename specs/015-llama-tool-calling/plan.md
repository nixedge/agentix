# Implementation Plan: Tool Calling for agentix-llama

**Branch**: `015-llama-tool-calling` | **Date**: 2026-08-21 | **Spec**: [spec.md](./spec.md)

## Summary

Add OpenAI-compatible structured tool calling to `agentix-llama`. The key insight: `LlamaChatTemplate::to_str()` exposes the raw Jinja2 template string stored in the GGUF. We replace the current `model.apply_chat_template()` call (which has no tools parameter) with a `minijinja` render of the same template string, passing `{messages, tools, add_generation_prompt: true}`. The model then generates `<tool_call>...</tool_call>` XML markers in its output, which we parse and convert into an OpenAI-style `tool_calls` array with `finish_reason: "tool_calls"`. No C++ library changes, no GPU-side changes — this is entirely template rendering and response parsing.

## Technical Context

**Language/Version**: Rust 2021, Rust 1.80+ (fenix stable via Nix)  
**New Dependency**: `minijinja = { version = "2", features = ["json"] }` in `agentix-llama`  
**Existing Dependencies in scope**: `llama-cpp-2 = "0.1"`, `agentix-api`, `agentix-infer`  
**Storage**: N/A (stateless per request)  
**Testing**: `cargo test -p agentix-llama`, `cargo test -p agentix-api`, `cargo test -p agentix-infer`  
**Target Platform**: Linux (NixOS), Unix socket server  
**Performance Goals**: Template rendering < 1ms (SC-004); zero regressions on tool-free requests (SC-003)

## Implementation Phases

### Phase 1: API Types (agentix-api)

**File**: `agentix-api/src/lib.rs`

1. Add `tool_calls: Option<serde_json::Value>` and `tool_call_id: Option<String>` to `ChatMessage` before the `#[serde(flatten)] extra` field, with `#[serde(skip_serializing_if = "Option::is_none")]` on each.

2. Add `tools: Option<Vec<serde_json::Value>>` to `ChatCompletionRequest` before the `#[serde(flatten)] extra` field, with `#[serde(skip_serializing_if = "Option::is_none")]`.

No new types needed — `serde_json::Value` carries the full tool/tool_call structures.

### Phase 2: Infer Types (agentix-infer)

**File**: `agentix-infer/src/lib.rs`

1. Add `tool_calls: Option<serde_json::Value>` and `tool_call_id: Option<String>` to `CompletionMessage`, with `#[serde(skip_serializing_if = "Option::is_none")]`.

2. Add `tools: Option<Vec<serde_json::Value>>` to `CompletionRequest`, with `#[serde(skip_serializing_if = "Option::is_none")]`.

3. Update `CompletionRequest::new()` constructor: leave `tools: None` (callers set it explicitly after construction, matching how `grammar` is handled today).

### Phase 3: minijinja Template Renderer (agentix-llama)

**Files**: `agentix-llama/Cargo.toml`, `agentix-llama/src/lib.rs`

1. Add to `Cargo.toml`:
   ```toml
   minijinja = { version = "2", features = ["json"] }
   ```

2. In `agentix-llama/src/lib.rs`, add a `ToolCallResult` struct (internal only):
   ```rust
   struct ToolCallResult {
       id: String,
       name: String,
       arguments: String,
   }
   ```

3. Add `parse_tool_calls(output: &str) -> Vec<ToolCallResult>`:
   - Use a simple string scan for `<tool_call>` / `</tool_call>` markers (no regex dep needed).
   - For each captured body: `serde_json::from_str::<serde_json::Value>(body)`, extract `name` (string) and `arguments` (re-serialize as string if object, or use as-is if already a string).
   - Generate a `uuid::Uuid::new_v4()` for each call's `id` (uuid crate already in workspace).
   - Return empty vec if no markers found.

4. Modify `apply_chat_template` signature to accept tools:
   ```rust
   fn apply_chat_template(
       model: &LlamaModel,
       messages: &[CompletionMessage],
       tools: Option<&[serde_json::Value]>,
   ) -> Result<String, String>
   ```

5. Implementation logic:
   - If `tools.is_none()` or `tools` is empty: use existing code path (`model.chat_template(None)` → `model.apply_chat_template()`). Zero behavioural change.
   - If `tools.is_some()` and non-empty:
     - Get raw Jinja2 string: `model.chat_template(None)?.to_str()?.to_string()`
     - Build minijinja `Environment` with `json` filter enabled (default in `json` feature).
     - Construct the messages context as `serde_json::Value::Array` — each message is a JSON object with `role`, `content`, and optionally `tool_calls` / `tool_call_id`.
     - Render with context: `{messages, tools, add_generation_prompt: true}`.
     - Return rendered string or map minijinja error to `String` error.

6. Update the `complete_sync` call site: pass `req.tools.as_deref()` as the third argument.

### Phase 4: Request Wiring (agentix-llama/src/main.rs)

**File**: `agentix-llama/src/main.rs`

In `chat_completions_handler`:

1. After parsing `api_req: ChatCompletionRequest`, extract:
   ```rust
   let tools = api_req.tools.clone(); // Option<Vec<serde_json::Value>>
   ```

2. When building `CompletionMessage` from each `ChatMessage`, also carry through:
   ```rust
   CompletionMessage {
       role: msg.role.clone(),
       content: /* existing extraction */,
       tool_calls: msg.tool_calls.clone(),
       tool_call_id: msg.tool_call_id.clone(),
   }
   ```

3. Set `req.tools = tools` on the `CompletionRequest` after construction.

### Phase 5: Response Serialization (agentix-llama/src/main.rs)

In the non-streaming response path (after `full_content` is accumulated from the chunk stream):

1. Call `parse_tool_calls(&full_content)`.
2. If result is non-empty:
   ```json
   {
     "choices": [{
       "index": 0,
       "message": {
         "role": "assistant",
         "content": null,
         "tool_calls": [
           {"id": "call_<uuid>", "type": "function", "function": {"name": "...", "arguments": "..."}}
         ]
       },
       "finish_reason": "tool_calls"
     }]
   }
   ```
3. If result is empty: existing response construction unchanged (`content: full_content`, `finish_reason: "stop"` or `"length"`).

If `parse_tool_calls` finds a marker but the JSON body is unparseable, return HTTP 500 with `{"error": "tool call parse error: <detail>"}`.

### Phase 6: Tests

**Unit tests** in `agentix-llama/src/lib.rs` (or `agentix-llama/tests/tool_calling.rs`):

- `parse_tool_calls_single` — input with one `<tool_call>{"name":"todo_list","arguments":{}}</tool_call>`, assert one result with correct name and `arguments == "{}"`.
- `parse_tool_calls_multiple` — two consecutive blocks, assert two results.
- `parse_tool_calls_none` — plain text with no markers, assert empty vec.
- `parse_tool_calls_malformed_json` — valid markers but invalid JSON body, assert… (either skip or propagate; define in implementation).

**Unit tests** in `agentix-api` (or inline):

- `chat_completion_request_deserializes_tools` — JSON with `tools` array round-trips correctly.
- `chat_message_deserializes_tool_calls` — assistant message with `tool_calls` field round-trips.
- `chat_message_deserializes_tool_call_id` — tool result message with `tool_call_id` round-trips.

**Integration test** (agentix-llama, requires fixture GGUF with tool-calling template):

- `tool_call_response_shape` — POST to `/v1/chat/completions` with a `tools` array and a question that should trigger a call; assert `finish_reason == "tool_calls"` and `tool_calls[0].function.name` is non-empty.
- `no_tool_regression` — POST without `tools`; assert response is unchanged.

Note: The fixture GGUF (small model pinned in Nix) may not have a Qwen2.5 tool-calling template. If the unit tests for `apply_chat_template_with_tools` are not feasible against the fixture, they are skipped with `#[ignore]` and validated manually against the production model (see quickstart.md).

## Key Constraints

- **Template rendering path**: minijinja is only invoked when `tools` is `Some` and non-empty. The existing `model.apply_chat_template()` code path is unchanged for all tool-free requests — zero regression risk.
- **`tool_call_id` generation on parse**: each parsed tool call gets a freshly generated `uuid::Uuid::new_v4()` formatted as `"call_<uuid>"`. This is what the harness uses for the follow-up `role: "tool"` message's `tool_call_id`.
- **`clippy::unwrap_used` / `expect_used`**: parse errors map to `String` errors via `map_err`; all minijinja errors are `?`-propagated to the caller as `String`.
- **Streaming + tools**: `tools` field in a streaming request is silently ignored (streaming path doesn't touch `req.tools` since `apply_chat_template` still receives it but the response writer never calls `parse_tool_calls`). Add a `tracing::warn!` noting that streaming tool calling is not yet supported.
- **minijinja template compatibility**: Qwen2.5-Instruct's template uses `tojson`, `namespace()`, `for`, `if`, `loop.last` — all supported by minijinja 2.x with the `json` feature. If a future model's template uses unsupported Jinja2 features, `apply_chat_template_with_tools` will return an error and the caller receives a 500.
